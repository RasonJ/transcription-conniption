Transcription Conniption walkthrough

I used the running web build at localhost:8081 the way a researcher would. I read the Pedro Nunes sample, edited its HSMS source, ran the concordance and the assistant, exported, and opened a Celestina witness from the Library. Below are the 11 problems I found, ranked by how much they get in the way of research. Each one is marked on the screen where it happens.

Tested in the desktop app's browser pane at 705 px wide (roughly a tablet or a half-width laptop window), plus a 375 px phone viewport. I removed my test edits from the sample afterward.

Broken gives wrong results or blocks the task Confusing works, but misleads or slows people down Polish cleanup, accessibility, wording

Fix these first

  1. Make the parchment fit the screen. Below about 740 px the right edge is cut off, which hides glosses, catchwords and the leaf label. On a phone the text is clipped on both sides.
  2. Keep one validation result. While you type, the two validation panels show different results, and the structural check only runs once the editor loses focus.
  3. Make the validator, the renderer and the samples follow the same rules. A catchword left open inside a column passed without comment. Meanwhile the sample's own gloss uses {GLR.}, which isn't in the HSMS manual (the manual uses {GL. [^text]}, §3.239a): the page view draws it as a gloss while the linter flags it.
  4. Stop using Spanish lemmas for Portuguese. The concordance files 5 of the 6 copular he in Nunes under haber.
  5. Make buttons and switches real controls. Most of them can't be reached with a keyboard or screen reader.

Findings

BrokenStudio · Parchment, reader and editor modes

1. The parchment is cut off below about 740 px

The folio has a fixed width inside a container with overflow-x: hidden (734 px of content in a 667 px box). Anything past the right edge can't be reached: the leaf label (1), the marginal gloss (2) and the catchword (3). On a 375 px phone the main text is also clipped on the left, and the page shows only about ten lines before blank space.

Fix: scale the folio to the container width (SVG viewBox or a CSS transform), so every element stays proportionate. Add pinch and zoom controls for close reading. If the page has to stay at native size, use horizontal scrolling with a visible edge shadow instead of hiding the overflow.

BrokenStudio · Advanced editor → Transcription Code

2. The two validation panels disagree while you type

I added a test line {ZZZ. test} at the top. The line-level banner (1) updated at once: 2 warnings, at L1 and L20. The structural panel just below it (2) kept showing the old result: 1 warning at L19. "Parsing manuscript structure…" (3) stayed on screen for more than 14 seconds and only cleared once I clicked outside the editor.

So the same warning appears in three places (banner, panel, full sheet) with different counts and different line numbers. That's the moment researchers stop trusting the checker.

Fix: show a single validation list. Run the structural pass on the same debounce as the line checks, not on blur. If it must lag, gray out the stale entries and show a spinner that actually finishes.

BrokenLinter / structural validation

3. Real errors pass, and the parts of the app follow different rules

  • Missed: I typed {CW. a right after {CB1., which puts a catchword inside the column with no closing brace. Manual §4.2 says the catchword goes on its own line after the column's closing brace. Neither panel reported it, and the unbalanced brace went unflagged too.
  • Inconsistent: the bundled sample marks its gloss with {GLR.}. That isn't in the manual's mnemonic list; §3.239a uses {GL. [^text]}. The page view still draws it as a margin gloss, while the linter calls it an "unrecognized HSMS tag" (1). So the parser and the linter use different tag catalogs, and the first thing a new user sees is a warning on your own demo.
  • Message: (2) tells the user to "verify against the mnemonic catalog" but doesn't link to it, cite a manual section, or offer a fix.

Fix: build the linter's and the parser's tag lists from one registry taken from the manual's mnemonic index, and mark any app-only tags as extensions. Rewrite the sample's gloss as {GL. [^…]}. Add brace-balance and placement rules (§3.239a(e) close inside the column, §4.2 catchword and signature, §3.12 column end, §5.1 remark periods), and give every message a manual section and a one-tap fix where one exists.

BrokenStudio · Concordance

4. Portuguese text gets Spanish lemmas

Nunes's Tratado da sphera is Portuguese, but the concordance lemmatizes it with the Old Spanish dictionary. In five of the six hits under haber, he is the Portuguese copula "é" ("a primeira he sustancial"). The list also shows atar (from ate, "até"), acid (a truncated acidẽtal) and tu. A researcher who exports these counts gets wrong numbers without any warning.

Smaller issues: the keyword isn't centered in a fixed column (as is standard for KWIC), hits show the folio but not the line, the scrollbar covers the counts, and there is no export from this drawer.

Fix: lemmatize only when the witness language matches the dictionary. Otherwise group by surface form and say why ("Lemmas available for Old Spanish only"). Show the surface form next to each lemma, so wrong mappings are easy to spot.

ConfusingStudio · toolbar and validation

5. Error counts and line numbers don't match

  • The button reads Errors (1) (B), but the sheet it opens says "0 errors · 1 warning". Call it "Issues", or show both counts.
  • The same item is called "L19" (line in the source file) and "13" (manuscript line) on the same row, with no label for either.
  • "Jump to line on canvas" sets the focus bar but doesn't highlight or scroll to the target line. There's no jump to the source line, which is where the fix happens.

Fix: label the two numbers ("source line 19 · ms. line 13"), highlight the target line, and add "Edit this line", which opens the code view with the cursor on that line.

ConfusingStudio · Transcription Code

6. The source editor is a plain text box

  • There are no source line numbers, so "L19" can't be found except by counting.
  • The browser spellcheck is on (spellcheck=true), so nearly every Old Portuguese word gets a red squiggle. That looks like an error and competes with the real ones.
  • Code and parchment are alternate tabs, so you can't see a change and its result together. At this width that's reasonable, but on a desktop window they should sit side by side.
  • The editor sits below the toolbar, the editor tools and the validation panels, so it's the fourth thing on the screen in a mode built for editing.

Fix: turn spellcheck off, add a line-number gutter, show code and parchment side by side above about 1000 px, and move validation into a collapsible strip under the editor.

ConfusingStudio · editor tools, display toggles, exports

7. Too many controls, too much jargon

  • Sample loaders (Nunes demo, Simple, LAT span, Graphics) sit in the same row as file actions (New blank scriptorium, Batch folder, Import/Export .hsms). A researcher can't tell which ones replace their work.
  • Thirteen display toggles sit in one flat grid. Off is red and on is teal, so the off state looks like an error, and color is the only cue. Group them by purpose: Text (expansions, deletions, diacritics, MUFI), Layout (line numbers, reading flow, facsimile, figures), Compare (synoptic, modern text).
  • Exporting has three separate entry points: the Export sheet (txt/html/svg/png/jpg), a separate TEI export button, and Export .hsms in the editor tools. TEI, the format scholars most need, isn't in the Export sheet. One choice there is described as "Legacy table layout for browsers", which makes it sound like the wrong one to pick.
  • "Scriptorium", "PUA", "otiose", "SVG canvas" and "Place figure" are developer terms. Each label should say what the user will see change.

Fix: make one Export sheet with every format (TEI and .hsms included), a "Samples" menu separate from file actions, and grouped toggles with plain labels and an on/off cue that doesn't rely on color.

PolishStudio · Assistant

8. Unexplained badges on assistant answers

The answer is good and can be reproduced. Around it, though, sit unexplained badges: "A · Exact" (1), a bare "64%" (2), and a developer timer, "4.90 ms" (3). The chip counts (e.g. "Zipf 62") don't say what they count.

It also says sphera occurs 4 times, while the concordance shows esfera 6, because the assistant counts exact word forms and the concordance groups by lemma. Neither one explains the difference.

Fix: hide the timer outside dev builds. Turn the tier and the percentage into plain words with a tooltip ("Exact count · matched 64% of the question"). Add one line: "Exact form only. Including spheras: 6."

PolishLibrary

9. Library entries are named after their files

Entries show the file path instead of a title: "1500/auto 02 (Celestina)". The first entry is ". desconocido" (1). Celestina takes up about 40 separate rows (2), one per act file, which buries everything after it. Opening a witness shows its file name, not its title and author.

Fix: show the title, author, date and shelfmark from the catalog, group parts of the same work under one entry, and sort by author or date with a choice of order.

PolishWhole app · accessibility

10. Most controls aren't real buttons

In the accessibility tree, Advanced editor, Export, Concordance, TEI export, Errors, every editor tool and every "Open in Studio" link show up as plain generic elements, not buttons. All 13 display switches are announced only as "on", with no name. The bottom tabs have no names either. Keyboard and screen-reader users can't operate most of the Studio.

Fix: give every Pressable accessibilityRole="button" and a label, label each Switch, and name the tab-bar items. Then check it with a keyboard-only pass.

PolishSources tab

11. Developer text on the Sources page

  • The language list includes the pseudo-locale [Ëñglîsh ~~~]. Hide it outside dev builds.
  • The description reads as a spec: "real-time vector rendering engine… precise coordinate vector metrics". It also mentions "MCP: audit_hsms_syntax" and the repo path "docs/OSTA-guide.md", neither of which means anything to a researcher.
  • The language picker opens the Sources page, but most people will look for it next to the language chip in the Studio header.

Fix: rewrite the intro in two sentences a paleographer would write. Link the OSTA guide as a page, not a file path.

I didn't test PDF or image ingest (it needs the backend), batch folders, or a facsimile with a real image attached, so a pass with the backend on would round this out. Earlier I suggested suggested-question chips, a method line and result export for the assistant; those are already built.
